Lifelong Mapping and 3D Change Detection on Object-Level Scene Graphs

This guide explains the project from the beginning. It assumes no background in robotics or 3D vision. Every technical term is explained the first time it matters, and the sections build on each other, so it is best read in order the first time.

Team: Ch Shreyash, Farzana S, Prajas Wadekar Status as of 4 November 2026 Code: github.com/PrajasW/LM-3DCD-SG

01The problem this project solves

Imagine a robot that works in an office, a lab or a home. It visits the same rooms again and again, maybe once a day, maybe once a month. Between visits, people change things. A chair gets pushed to another desk, a box appears in a corner, a lamp is taken away. The robot keeps a map of each room from its earlier visits, and it wants to use that map again when it comes back.

When the robot returns, it has three jobs.

  1. Find where it is inside the old map. When the robot starts a new visit, it does not know where it is relative to its old map. It has no starting estimate, because it may have been switched off, carried around, or started from a different door. This job is called relocalization. It is harder than it sounds because some of the things the robot would normally recognise to orient itself (the furniture) may have moved.
  2. Work out what changed. For each object in the room, the robot should decide whether it stayed in place, moved somewhere else, was removed, or is new. There is a fifth answer that is easy to forget: the robot might simply not have looked at that part of the room on this visit, or the object might be hidden behind something. In that case the honest answer is "not observed", and the robot should not claim the object is gone. This job is called change detection.
  3. Update the map. The stored map should be edited to reflect the changes, object by object, so that it stays correct over many visits.

Two simple approaches to the third job do not work well, and it helps to see why. The first is to throw away the old map and replace it with whatever the robot sees now. This deletes every part of the room that the robot did not look at during this visit, it forgets which object is which (so the robot cannot say "this is the same chair as last week"), and it changes the coordinate system of the map every time. The second is to keep adding each new scan on top of the old ones. Then the map contains outdated copies of everything that moved, and its size grows with every visit, even if the room itself stays the same size.

This project proposes a pipeline that does all three jobs on every visit. It needs no training data (no neural network is trained), and it does not need anyone to tell it how the new visit lines up with the old map. The aim is a map whose size depends on how many objects are in the room, not on how many times the robot has visited.

The core idea in one paragraph

If two objects did not move between visits, the distance between them is the same in both visits. This is true no matter where the robot is standing or which way it is facing. So if we guess which object in the new visit corresponds to which object in the map, we can check every pair of guesses: do the two distances agree? The largest group of guesses in which every pair agrees must be the objects that stayed in place, and those objects tell us where the robot is. Smaller groups that agree among themselves are objects that moved together, such as a desk and the monitor on top of it.

02Background concepts

This section explains the vocabulary used in the rest of the guide. If you already know a term, skip it.

How a robot sees a room in 3D

Depth camera and depth image
A normal camera records colour for each pixel. A depth camera (also called an RGB-D camera, for red, green, blue and depth) also records how far away the surface at each pixel is. A depth image is a grid of distances. Phones with face unlock and devices like the Microsoft Kinect have depth cameras. The 3RScan dataset used here was recorded with a tablet that has a depth sensor.
Point cloud
If you take every pixel of a depth image and compute its position in 3D space (using the distance and the camera's known lens properties), you get a set of 3D points. Combining many depth images taken while walking around a room gives a point cloud of the whole room: a list of millions of (x, y, z) coordinates lying on the surfaces of the walls, floor and furniture. A mesh is a similar representation in which neighbouring points are joined into small triangles.
Segmentation and instances
A raw point cloud does not know which points belong to which object. Segmentation splits the points into groups, one group per object. An instance is one specific object: "chair number 3" rather than just "chair". In this project, each object in the room is one instance with its own set of points and a class label such as chair, table or lamp.
Centroid, extents and bounding box
The centroid of an object is the average position of its points, which is roughly its centre. The extents are its sizes along three directions (length, width, height). A bounding box is the smallest box that encloses the object.

Position and orientation

Coordinate frame
To write down a position you need an origin and three axes. Each scan of a room has its own coordinate frame, usually wherever the camera was when recording started. Two scans of the same room are therefore written in different coordinate frames, and the same chair has different coordinates in each.
Pose and rigid transform
The pose of the robot is its position and its orientation (which way it is facing and tilted). Mathematically, moving from one coordinate frame to another is a rigid transform: a rotation followed by a translation (a shift). It is called rigid because it does not stretch or bend anything; all distances between points stay the same. A rigid transform in 3D has six numbers of freedom: three for rotation and three for translation. It is usually stored as a 4 by 4 matrix, written T in this guide. Relocalization means estimating the T that maps the new visit's coordinates onto the map's coordinates.
Rotation error and translation error
When we compare an estimated pose with the true one, the rotation error is the angle (in degrees) of the leftover rotation between them, and the translation error is the distance (in metres or centimetres) between the estimated and true positions. In papers these are often abbreviated RRE (relative rotation error) and RTE (relative translation error).

Scene graphs

3D scene graph
A graph in computer science is a set of nodes connected by edges. A 3D scene graph describes a room this way: each object is a node, and an edge between two nodes records a relationship, such as "the monitor is standing on the desk" or "the chair is close to the table". Each node also stores information about its object: its points, centroid, size, class label and so on. The advantage over a plain point cloud is that the room is described object by object, so a change can be described object by object too ("chair 3 moved 2 metres to the left").
Object-level map
In this project the map is a scene graph whose nodes are the room's objects. Editing the map means editing nodes: moving a node, deleting a node, adding a node. The floor, walls and ceiling are stored as special structural nodes because they do not move.

Standard tools from geometry and registration

Registration
Registration is the general task of finding the rigid transform that lines up two point clouds of the same scene. Relocalization in this project is a registration problem: line up the new visit with the map.
Correspondence
A correspondence (or match) is a claim that something in one scan is the same thing as something in the other scan. For example, "object 7 in the map is object 12 in the new visit". If you have three or more correct correspondences between points that are not all on one line, you can compute the rigid transform exactly. The hard part is that many proposed correspondences are wrong, and wrong ones are called outliers.
Kabsch algorithm (also called Umeyama alignment)
Given a list of matched point pairs, the Kabsch algorithm computes the rotation and translation that best lines them up, in the least-squares sense (it minimises the sum of squared distances between matched points after the transform). It is fast and exact, but a single badly wrong match can pull the answer far away, so the matches must be cleaned first.
ICP (Iterative Closest Point)
ICP refines a rough alignment. It repeats two steps: for each point in one cloud, find the closest point in the other cloud; then compute the transform that best lines up those closest pairs. It converges to an accurate answer only if it starts close to the correct one, because if the starting guess is far off, the "closest points" are the wrong points. The variant used here, point-to-plane ICP, measures the distance from a point to the surface around its partner, which converges faster on walls and floors. ICP reports a fitness: the share of points that ended up within a small distance of the other cloud.
RANSAC
RANSAC (random sample consensus) handles correspondences with many outliers. It repeatedly picks a few correspondences at random, computes a transform from them, and counts how many other correspondences agree with that transform. After many tries it keeps the transform with the most agreement. It works well but can be slow, because it may need many random tries when most correspondences are wrong.
FPFH features
FPFH (Fast Point Feature Histograms) is a hand-designed description of the local surface shape around a point, computed from the angles between the surface directions (normals) of its neighbours. Points on similar-looking surfaces get similar FPFH descriptions, so matching FPFH descriptions between two scans gives point correspondences without knowing anything about objects. Many of these matches are wrong, which is why FPFH is paired with RANSAC or TEASER++.
Maximum clique
In a graph, a clique is a group of nodes in which every node is connected to every other node. The maximum clique is the largest such group. This project builds a graph whose nodes are proposed matches, connects two matches if they are geometrically compatible, and takes the maximum clique as the set of matches that all agree with each other. Finding the maximum clique is hard in general, but the graphs here have only tens of nodes, so it takes about a millisecond.
Free space
If a depth camera sees a wall 4 metres away in some direction, then the space along that line of sight, up to the wall, must be empty. This is how the robot can tell "the object is gone" (the camera now sees through the place where it used to be) apart from "I did not look there" (no line of sight passed through that place). This idea is the basis of Step 5 of the method.

Learned versus training-free methods

A learned method uses a neural network whose parameters were fitted on a training dataset. It can pick up patterns that are hard to describe by hand, but it may behave poorly on inputs that differ from its training data, and it needs that training data in the first place. A training-free method uses only hand-designed rules and geometry. This project is training-free: every part of it is a geometric rule with a few thresholds, and those thresholds were set by looking at a small set of development rooms.

03The dataset: 3RScan and 3DSSG

3RScan (Wald et al., ICCV 2019) is a dataset of 1,482 scans of 478 indoor rooms such as offices, bedrooms, kitchens and cafés. Each room was scanned between 2 and 12 times, with gaps between scans that range from minutes to months, and the rooms changed in between. For each room, one scan is chosen as the reference scan, and the others are called rescans. This structure matches the project's setting exactly: the reference scan plays the role of the stored map, and each rescan plays the role of a later visit.

For every scan, 3RScan provides the following:

  • the RGB-D frames (colour and depth images) with the camera's pose for each frame;
  • a reconstructed mesh of the room;
  • instance labels: every point is assigned to an object, and the object IDs are the same across all scans of a room, so "object 17" is the same physical chair in the reference scan and in every rescan;
  • the true rigid transform that aligns each rescan to its reference scan (this is the ground truth for relocalization);
  • a list of which objects moved between the reference and the rescan, with their motion, and which were removed (this is the ground truth for change detection).

3DSSG (Wald et al., CVPR 2020) adds a scene graph to every 3RScan scan. It lists each object's class (534 classes in total) and relationships between objects (41 types, such as "standing on", "attached to" and "close by").

The dataset has three splits. The train split is what learned methods train on. The validation split (47 rooms with 110 rescans in total) is used for reporting results here. The test split has no published ground-truth transforms, so it cannot be scored.

How the data is used in this project

  • Phase 1 uses the annotated segments. The object segmentation and class labels come from the dataset annotations, not from a segmentation network. This isolates the question "does the matching and pose method work?" from the question "is the segmentation good?". Phase 2 will replace the annotations with predicted segments.
  • The data came from a Hugging Face mirror of 3RScan (maartenImjalli143/3RScan), because the official download server is very slow from the university cluster. Only the label files are needed for relocalization (about 0.6 GB for the whole validation split). The depth sequences (about 6.8 GB) are needed only for Step 5.
  • Three sets of rooms were used. A development set of 6 rooms from the train split (22 pairs) was used to choose all thresholds. A small validation subset of 4 rooms (17 pairs) was used for the mid-submission. The full validation split (47 rooms, 110 pairs) is being run now. Because thresholds were chosen only on the development rooms, the validation numbers are a fair test.

Building the scene graph

Each scan is turned into a scene graph. The code is in lifelong/graph.py.

  • Floor plane. The points labelled "floor" are used to fit a flat plane. Its upward direction (the floor normal) tells us which way is up in this scan's coordinate frame. This matters because each scan's coordinate frame is arbitrary, so "up" is not necessarily the z axis.
  • Structural nodes. Floor, wall and ceiling segments become structural nodes. They are not matched as objects, but their points help the final pose refinement.
  • Object nodes. Every other segment with at least 50 points becomes an object node. Each node stores its points, its centroid, its class label, its height above the floor, and its extents.
  • Extents that do not depend on the robot's pose. The extents are computed in a way that gives the same numbers no matter how the scan is rotated. The vertical extent is measured along the floor normal. The two horizontal extents are taken from the smallest rectangle that encloses the object's footprint on the floor. An earlier version used principal component analysis (PCA) for the horizontal axes, but for objects with a square footprint (a square table, for instance) PCA picks arbitrary axes, and the reported sizes changed with the scan's orientation. Extents are measured between the 2nd and 98th percentile of the points so that a few stray points do not inflate them.
  • Edges. Edges come from the 3DSSG relationships, plus a "near" edge between any two objects whose surfaces are within 30 cm of each other. The edges are not used by Steps 1 to 3 yet; they are kept for the map editing in Step 6.

Step 1: candidate matches

The goal of Step 1 is to propose, for each object in the map, a few objects in the new visit that could be the same object. The proposals only use properties that do not change when the robot moves: the class label, the three extents, and the height above the floor. Positions are not used here, because the robot does not know yet how the two coordinate frames relate.

Two objects are compared only if they have the same class label. For two objects a and b of the same class, the code computes a cost (lower means more similar):

cost(a, b) = |log(length_a + 0.05) − log(length_b + 0.05)| + |log(width_a + 0.05) − log(width_b + 0.05)| + |log(height_a + 0.05) − log(height_b + 0.05)| + |h_a − h_b| / 0.3 m

Here h is the height of the object's centre above the floor. Using logarithms means the cost reacts to relative size differences: a 10 cm difference matters a lot for a cup and very little for a sofa. The small constant 0.05 prevents very thin objects from producing huge values. Pairs with a cost above 2.5 are discarded.

Each map object then keeps its 3 cheapest candidates in the new visit, and each new-visit object keeps its 3 cheapest candidates in the map. Keeping several candidates is deliberate. A room often contains several identical objects (six identical office chairs, for example), and size and class cannot tell them apart. Instead of guessing, Step 1 passes all plausible options on, and Step 2 uses geometry to pick the right one. A typical validation pair has about 23 objects in the map and about 29 candidate matches.

Step 2: the largest group of matches that agree

This is the core of the method (lifelong/consistency.py). Take any two candidate matches, say map object A matched to new object A′, and map object B matched to new object B′. If both matches are correct and neither object moved, then the distance from A to B in the map must equal the distance from A′ to B′ in the new visit. The robot's position does not matter, because a rigid transform does not change distances.

The step works like this:

  1. Build a compatibility graph. Every candidate match from Step 1 is a node. Two matches are connected by an edge if they pass three tests:
    • they are one-to-one: they do not use the same map object twice or the same new object twice;
    • the distance between the two objects is the same in both visits, within a tolerance;
    • the difference in height above the floor between the two objects is the same in both visits, within the same tolerance. This test rejects mirror-image arrangements, which have the same distances but are upside down or flipped.
  2. Allow for measurement noise and partial views. The tolerance is τ = 0.10 m + 0.10 × (r + r′), where r and r′ are the radii of the two objects (half the diagonal of their extents). The fixed 10 cm covers sensor and annotation noise. The radius term exists because if only part of a large object is visible (half a sofa, for instance), its centroid shifts toward the visible half. Larger objects therefore get a larger tolerance.
  3. Take the maximum clique. The maximum clique of this graph is the largest set of matches in which every pair passes the test. This set is called the static set S: the objects that, as far as the method can tell, did not move. The clique is found with the igraph library; ties between equally large cliques are broken by choosing the one with the lowest total Step 1 cost.
  4. Repeat on what is left. After removing the static set's objects, the code searches for the next largest clique among the remaining matches, and so on. These smaller consistent groups are candidates for objects that moved together. They are stored now and will be used in Step 4.

This idea is not new at the level of individual points. PCM (2018) and TEASER (2021) use the same maximum-clique test on point correspondences or loop closures. What is different here is that the test is applied to whole objects. A room has tens of objects instead of thousands of points, so the problem is far smaller and takes about 1.5 milliseconds. The groups also have a direct meaning: the largest group is the static part of the room, and the other groups are objects that moved together.

Step 3: computing the pose, or declining

Once the static set is known, the pose is computed in two stages (lifelong/pose.py).

  1. Rough pose from centroids. The Kabsch algorithm computes the rotation and translation that best lines up the centroids of the static objects in the new visit with their centroids in the map. Each object is weighted by 1 / (0.1 + radius), so small objects, whose centroids are more reliable, count more. The two floor normals are added as an extra pair of directions that must line up. This uses the fact that "up" is the same physical direction in both visits.
  2. Refinement with ICP. Point-to-plane ICP is run on the points of the static objects plus the floor and walls, starting from the rough pose. It runs three rounds with matching distances of 30 cm, 10 cm and 5 cm, on points thinned to a 5 cm grid. ICP roughly halves the error of the centroid-only pose.

The method also refuses to return a pose when the evidence is weak. In that case it returns "no pose" (written ⊥ in the report) and gives a reason. It declines in three situations:

  • too few static objects: fewer than 3 objects in the static set;
  • degenerate layout: the static centroids lie almost on one line, which leaves the rotation around that line undetermined (measured by the spread of the centroids, which must be at least 20 cm in the second direction);
  • poor alignment: after ICP, fewer than 30% of the points lie within 5 cm of the map.

In the evaluation, declining counts as a failure, exactly like a wrong pose. So a method cannot improve its score by declining. Declining is still useful for a real robot, because a wrong pose leads to wrong change labels and a corrupted map, while "no pose" lets the robot try again from another viewpoint.

Step 4: objects that moved planned

Each smaller consistent group from Step 2 is a set of objects whose distances among themselves stayed the same, but which do not fit the static set. Most likely they moved together, for example a desk and the monitor and keyboard on it. Their common motion can be computed with the same Kabsch and ICP procedure as in Step 3. A single object that moved alone has no partner to compare distances with, so it cannot form a group. For such an object, the plan is to align its old and new points directly with ICP, and to label it as moved only if the alignment fits well and Step 5 confirms that its old location is now empty.

Step 5: removed, added or not observed planned

A map object with no match in the new visit was either removed or simply not seen. To decide which, its points are moved into the new visit's coordinate frame using the pose from Step 3, and then projected into each depth image of the new visit using that frame's camera pose. There are three possible outcomes:

  • if the depth images show surfaces behind where the object used to be, the camera looked through that space and found it empty, so the object is labelled removed;
  • if the depth images show something in front of that place, the object may just be hidden, so it is labelled not observed;
  • if no depth image covered that place at all, it is also labelled not observed.

The reverse applies to new objects with no match in the map. Such an object is labelled added only if its space was seen to be empty on an earlier visit. If that space was never observed before, the object is inserted into the map but not counted as a change, because it may have been there all along. This requires the map to keep a record of which space has been observed empty.

Step 6: editing the map planned

The map is updated object by object:

  • static objects receive the new points;
  • moved objects are shifted by their computed motion;
  • removed objects are deleted;
  • added or newly observed objects are inserted;
  • objects that were not observed are kept unchanged.

Each object keeps a change history, edges are recomputed around edited objects, and the record of observed free space is updated. Because objects are edited rather than duplicated, the map's size depends on the number of objects in the room and does not grow with the number of visits.

05Related work (literature review)

The project sits where four lines of research meet. Each line solves part of the problem. None of the existing methods solves all of it.

3D scene graphs

Armeni et al. (2019) introduced the idea of a layered 3D scene graph for a building, with layers for the building, rooms, objects and cameras. Kimera (Rosinol et al., 2021) and Hydra (Hughes et al., 2022) build such graphs live while a robot explores, using SLAM (simultaneous localization and mapping). They assume that objects stay where they are and that only agents (people and robots) move. 3DSSG (Wald et al., 2020) labels every 3RScan scan with an object-level scene graph and trains a network to predict these graphs from point clouds. SceneGraphFusion (Wu et al., 2021) predicts the graph incrementally from RGB-D video. ConceptGraphs (Gu et al., 2024) attaches image features to object nodes so that objects can be searched with free-text queries. The common limitation is the update rule: either the world is assumed static, or objects that are not detected again are deleted, even if the robot never looked at them. This project reuses the scene-graph representation but makes the per-visit edit explicit and based on evidence.

Scene-graph alignment and relocalization

RIO (Wald et al., 2019) introduced 3RScan and the task of finding an object again in a later scan. SGAligner (Sarkar et al., ICCV 2023) aligns two scene graphs. A neural network turns each object into a vector (an embedding) based on its points, its relations and its attributes. Objects with similar vectors are matched, and the transform is computed from point matches on the matched objects. SG-PGM (Xie et al., CVPR 2024) treats alignment as partial graph matching and uses the object matches to re-score point matches. SG-Reg (Liu et al., T-RO 2025) uses a lighter network and a robust back-end to generalise better. SGAligner++ (2025) adds language features. All of these are trained networks, and they are evaluated mostly on pieces cut from the same scan. They also ignore objects they cannot match, so they do not report what changed. ROMAN (Peterson et al., 2025) aligns object maps for global localization using CLIPPER, without training, and is the closest relative of Step 2.

Consistency-based matching and robust registration

Joint compatibility (Neira and Tardós, 2001) and PCM (Mangelson et al., ICRA 2018) choose the largest set of measurements that are all consistent with each other. PCM does this with a maximum clique, for loop closures between robot maps. CLIPPER (Lusk et al., ICRA 2021) relaxes the maximum clique into a weighted problem that is faster to solve. TEASER (Yang et al., T-RO 2021) and later maximal-clique registration methods apply the pairwise distance test to point matches and remain accurate when more than 95% of the matches are wrong. The classical recipe for registering two point clouds without an initial guess is FPFH features plus RANSAC, followed by ICP. This project takes the pairwise test from points up to objects. That makes the problem much smaller, and it gives the consistent groups a meaning (static versus moved together).

Change detection and long-term mapping

Objects Can Move (Adam et al., ECCV 2022) finds moved, added and removed parts between two scans that are already aligned, by comparing depth images and grouping points that moved with the same rigid motion. Its output is unlabelled point clusters rather than objects. Living Scenes (Zhu et al., CVPR 2024) relocalizes and reconstructs objects across 3RScan rescans, again given the alignment. DSG (2026) labels objects as stable, appeared or missing by comparing renderings with images, using ground-truth poses, and has no "moved" state: a moved object becomes a missing object plus a new one. 3D VSG (Looper et al., 2023) predicts how likely each object is to change, but does not check whether it actually did. Panoptic Multi-TSDFs and Khronos (Schmid et al., 2022 and 2024) keep object-level maps consistent while things change during one continuous mapping session, and LT-mapper does lifelong LiDAR mapping after alignment.

06The baselines

A baseline is an existing method that is run on exactly the same data as the new method, so the results can be compared fairly. Four baselines were run, in two groups. Every method receives the same input for each pair: the reference scan, and the rescan moved by the same stored random rotation and shift. All of them are scored by the same script.

Group 1: learned scene-graph aligners

These are the methods most similar to this project, because they also work with object-level scene graphs. Both were run with the checkpoints (trained network weights) released by their authors, which were trained on the 3RScan train split. All evaluation rooms come from the validation split, so the networks have never seen them. Both receive the ground-truth object segments, just like this project's method.

SGAligner (ICCV 2023)

  • For each object, a network combines four kinds of input into one vector: the object's points (encoded by a point transformer), the graph structure (encoded by a graph attention network), its relations, and its attributes.
  • Objects are matched by vector similarity, keeping the 2 most similar candidates per object (the best setting reported in the paper).
  • The pose is computed by GeoTransformer, a learned point-matching network (here the version trained on the 3DMatch dataset), followed by GC-RANSAC.
  • A fix was needed to run it fairly. The GC-RANSAC library returned no answer at all on 53% of pairs, because its sampling strategy expects the matches to be sorted by confidence. A small patch sorts them and retries with uniform sampling when needed. This patch helps SGAligner.

SG-PGM (CVPR 2024)

  • It matches the two scene graphs with a learned partial graph matcher and then uses those object matches to re-weight GeoTransformer's point matches.
  • It was run with the authors' own model code, dataset loader and data batching code, unchanged. The only change was switching off its own random rotation, because the rescan is already moved by the stored random transform.

Group 2: classical point-cloud registration

These methods use only the raw points. They do not use segments, class labels or a graph. They are strong, widely used, training-free methods.

  • Shared preprocessing. Both clouds are thinned to one point per 5 cm cube, and an FPFH description is computed for every point. The surface directions (normals) are flipped where necessary so that they all point toward the centre of the scan. Without this fix, the direction of a normal depended on the scan's coordinate frame, and FPFH+TEASER++ dropped from 82% to 41% success under the random rotation.
  • FPFH + RANSAC (Open3D library): points are matched by FPFH, keeping only matches that agree in both directions, then RANSAC runs for up to one million iterations. The result is refined with point-to-plane ICP at 20, 10 and 5 cm.
  • FPFH + TEASER++: up to 10,000 mutual FPFH matches are passed to TEASER++, which uses the same maximum-clique idea as Step 2 of this project, but on individual points. The same ICP refinement follows.

Methods that were only cited

SG-Reg (T-RO 2025) releases only a network trained on a different dataset (ScanNet) and a C++ back-end, so it could not be run on 3RScan. SGAligner++ (2025) has not released code. Their published numbers are listed in the results tables with a note that they use a different evaluation protocol.

Reading the comparison fairly

The comparison is not equal in what each method is given. This project's method and the two learned aligners get the ground-truth object segments and class labels. The FPFH methods get only raw points. So when FPFH+RANSAC does better on pose accuracy, it does so with less information, and that is a real point against this project on pose accuracy alone. In exchange, this project's method is much faster and returns object matches, which the change detection steps need. The planned Phase 2 experiment with predicted segments will remove the ground-truth advantage.

07How results are measured

The evaluation uses the two-visit setting: the reference scan is the map, and one rescan is the new visit. Each such combination is called a pair.

  1. A random transform per pair. Each rescan is moved by a random rigid transform before any method sees it. The rotation is drawn uniformly from all possible 3D rotations, and the shift is drawn uniformly between −2 and +2 metres along each axis. The transform is generated once and stored in a file, so every method gets exactly the same input. This simulates a robot that has no idea where it is.
  2. Ground truth. The correct answer combines 3RScan's alignment of the rescan to the reference with the inverse of the random transform. It is used only for scoring. (One detail that caused confusion: 3RScan stores its 4 by 4 matrices in column-major order, so they must be transposed when read.)
  3. Pre-aligned run. A second run gives every method the rescan already aligned to the reference. This is the setting in which the learned baselines were trained and evaluated by their authors. It serves as a check that the baselines were set up correctly, and as an upper bound for them.

Metrics

Success rate at the RIO thresholds
A pair counts as relocalized if the rotation error and the translation error are both within a threshold. Two thresholds from the 3RScan paper are used: 10 cm and 10°, and the looser 20 cm and 20°. The 20 cm / 20° number is the headline result.
Registration recall (RR)
The rescan's points are moved by both the estimated and the true transform, and the root-mean-square distance between the two results is computed. The pair counts if that distance is under 20 cm. SGAligner, SG-PGM and SG-Reg report this metric, so it lets our numbers be compared with theirs.
Median rotation and translation error
The typical error over the pairs where a pose was returned. The median is used instead of the mean so that one completely wrong pose does not dominate the number.
Time per pair
The time to compute the pose for one pair.
Static-set precision and recall
Only for this project's method. Precision is the share of matches in the static set that are correct (same object ID) and belong to objects that really did not move. Recall is the share of truly unchanged objects that ended up in the static set.

A pair on which a method declines to return a pose counts as a failure.

What these numbers show

  • The random transform does not affect our method. Its success rate is the same with and without the random transform, which is expected because nothing in Steps 1 and 2 depends on the coordinate frame.
  • The learned scene-graph aligners collapse under the random transform. SGAligner drops from 71–76% (pre-aligned) to 35%, and SG-PGM from 65% to 18%. The likely reason is that their networks read object points in world coordinates, so a rotated room looks like a different room to them. SG-PGM's own paper does test with random transforms, but it rotated only the points used for the final registration, not the objects fed to the graph matcher.
  • Our method ties FPFH+TEASER++ and is two pairs behind FPFH+RANSAC, while being about 13 times faster than TEASER++ and 37 times faster than RANSAC. Steps 1 and 2 together take about 1.5 ms; almost all of the 0.13 s is ICP.
  • ICP matters. It halves the translation error of the centroid-only pose (7.6 cm to 3.3 cm) and raises the 10 cm / 10° success from 53% to 71%.
  • The static set is only about 60% correct on this subset (precision 60.5%, recall 58.5%). According to the report, most errors are swaps between identical objects, which do not harm the pose because identical objects in a regular arrangement give almost the same alignment. They will matter for change detection, which needs the correct object-to-object matches.

How the method fails

Our method failed on 3 of the 17 pairs.

  • Repeated layouts (2 pairs, both in one café). The café has a row of identical table, chair and menu sets. If you shift the whole room by one set, 8 objects line up consistently, while the correct alignment only lines up 7, so the maximum clique picks the wrong answer. ICP cannot correct this because the café scan has few walls to anchor it. This is the most serious failure because the method returned a confidently wrong pose (off by 2.4 m on one pair, and by 179° and 6.3 m on the other) instead of declining. The ICP fitness on the second pair was 0.335, just above the 0.3 cutoff. FPFH+RANSAC also fails one of these two pairs.
  • Too few objects (1 pair). One rescan covers only a small part of the room, and only 2 static objects were found, so the method correctly declined.
  • Everything moved (development rooms). In some development rooms every object moved. Declining is the correct object-level answer there, but the floor and walls alone would still give the pose.

Concrete next steps, in order

  1. Let the full validation run finish and compare all methods on 110 pairs. This decides whether the gap to FPFH+RANSAC seen on the subset was real. The results will replace the 17-pair table in the final report.
  2. Study the 5 wrong poses and 7 declines on the full split. A wrong pose is worse than a decline, because it leads to wrong change labels and a corrupted map. Two possible guards: require the floor and walls to agree after ICP, or decline when the second-largest consistent group is almost as large as the first (which is the signature of a repeated layout). Then add the structure-only fallback for rooms with too few static objects.
  3. Build Step 4. It needs no depth data. The consistent groups are already produced by Step 2 (stored as moved_groups), and 3RScan's annotations of which objects moved, with their motions, are already loaded by Meta3RScan.changes(), so it can be scored immediately. Measuring the static-set errors per change type early will show whether the 70% static-set precision limits change detection.
  4. Build Step 5 using the depth sequences. Each sequence.zip contains, per frame, a depth image (.pgm), a colour image (.jpg) and the camera pose (.pose.txt), plus the camera parameters in _info.txt, which is everything needed to project object points into each frame.
  5. Build Step 6 and run the multi-visit setting, then move to predicted segments.
Risks to keep in mind
  • Predicted segments may not match one to one. A segmentation network may split one table into two segments or merge a chair with the table next to it. The matching will need to allow several segments to match one object.
  • Step 5 is the most data-heavy step. The depth sequences have hundreds of frames per scan, so frames will be subsampled to keep the projection fast.
  • The depth data is on the compute node's local disk. If later work runs on a different cluster node, the sequences have to be downloaded again (about 40 minutes).

11Check your understanding

These questions cover the points that are most likely to come up in a presentation or viva. Try to answer each one before opening it.

Why can the robot not simply use GPS or its last known position to relocalize?

GPS does not work reliably indoors and is not accurate to centimetres anyway. The last known position is not available because visits are separated by hours to months, the robot may have been switched off or carried, and each scan has its own arbitrary coordinate frame. The project therefore assumes no initial guess at all, which is simulated by moving each rescan with a random rigid transform.

Why does the distance between two objects identify objects that did not move?

A change of viewpoint is a rigid transform, which preserves all distances. If two objects both stayed in place, the distance between them is the same in both visits, regardless of where the robot is. If one of them moved, the distance usually changes. Checking distances therefore tests whether a pair of matches is consistent with both objects being static, without knowing the robot's pose.

Why does Step 1 keep three candidates per object instead of just the best one?

Rooms often contain several identical objects, and their class and size cannot tell them apart. Keeping only the best match would be a coin toss among identical chairs. Keeping several candidates lets Step 2 choose the right one using geometry: only the correct chair will have consistent distances to the other static objects.

Why does the tolerance in Step 2 grow with the size of the objects?

If only part of a large object is visible in one visit (half of a sofa, for example), the centroid computed from the visible points shifts toward that part. The distance between centroids then changes even though the object did not move. A larger tolerance for larger objects prevents correct static pairs from being rejected for this reason. The tolerance is 10 cm plus 10% of the sum of the two objects' radii.

What is the purpose of the height test in Step 2?

Distances alone cannot tell a configuration from its mirror image, since a reflection also preserves distances. Both visits share the same floor, so the difference in height above the floor between two objects must also be preserved. This rules out mirrored or upside-down solutions.

Why would the method decline to return a pose, and why is that counted as a failure?

It declines when there are fewer than 3 static objects, when the static objects lie almost on one line (so the rotation around that line is undetermined), or when ICP leaves fewer than 30% of the points close to the map. Declining is counted as a failure so that a method cannot improve its score by refusing difficult pairs. For a real robot it is still better than a wrong pose, because a wrong pose would produce wrong change labels and corrupt the map.

Why do SGAligner and SG-PGM perform so much worse with the random transform?

Their networks read the object points in world coordinates, so the embedding of an object depends on how the scan is oriented. They were trained and evaluated on scans that share one coordinate frame. When the rescan is rotated randomly, the same object produces a different embedding and the matching breaks down. With pre-aligned rescans they recover to 71–76% (SGAligner) and 65% (SG-PGM), which shows that the adapters themselves are working.

FPFH+RANSAC was more accurate on the 17-pair subset. What does this project's method offer in return?

Three things. It is about 37 times faster (0.13 s against 4.8 s per pair). It is unaffected by the random transform by design. And it returns object correspondences and a static set, which are exactly what change detection needs; FPFH methods return only a transform. Note also that FPFH achieves its accuracy with raw points only, while this project's method was given ground-truth segments, so the Phase 2 run with predicted segments is an important test.

What went wrong in the café room, and how could it be fixed?

The café has a row of identical table, chair and menu sets. Shifting the whole room by one set makes 8 objects line up, more than the 7 that line up in the correct alignment, so the maximum clique picks the wrong solution. Few walls are visible, so ICP cannot correct it. Proposed fixes are to check that the walls and floor agree after alignment, and to decline when the second-best consistent group is nearly as large as the best one.

How will Step 5 tell "removed" apart from "not observed"?

The object's old points are moved into the new visit's frame with the estimated pose and projected into the new visit's depth images. If the camera saw surfaces behind the object's old location, the space is empty and the object was removed. If something in front blocks the view, or the location was never in any camera's view, the object is kept and marked not observed. New objects are labelled added only if their space was previously seen empty.

Why should the map size not grow with the number of visits, and how does the design ensure this?

If every visit's scan were appended to the map, the map would contain outdated copies of moved objects and grow without bound. In this design the map is edited object by object: static objects get new points, moved objects are shifted, removed objects are deleted, and only genuinely new objects are added. The number of nodes therefore tracks the number of objects in the room.
